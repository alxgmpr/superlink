## Architectural correction (major)

The bridge is **even more stateless than the previous pivot suggested**.
The post-ACTIVE management replies (the 0x53 / 0x44 / 0x43 DL frames)
**are not computed locally on the bridge**. The controller computes
them and ships the resulting hex bytes to the bridge via `sendMessage`
calls. Idle capture shows:

```
RX  {"action":"sendMessage", ...}
RX  {"mac":"9041B22E9A53","data":"0b9311010d14","duty":true,...}
```

— that's the controller telling the bridge "transmit these 6 bytes to
this sensor next." The bridge's job is reduced to:
1. Listen on LoRa, decrypt UL frames, forward decrypted body upstream
   (`messageReceived` event with `data: "<hex>"`).
2. Receive `sendMessage` requests from controller, encrypt + transmit
   the literal `data` bytes over LoRa.

**Consequence for the open-gateway plan:** the 70-byte Class B grant we
spent days trying to trace via memset/memcpy hooks is **generated by the
UniFi Network app**, not the bridge. `sub_327c4` is just the bridge's
generic "transmit this hex string" path, not grant generation. To
replicate the grant we either:

1. RE the UniFi Network app's lorabr controller module (Java/whatever
   the controller is written in), OR
2. Build our own controller from scratch — which is the Y plan
   anyway.

Option 2 is now even more attractive: the bridge contract is small.

## Transport (confirmed via plaintext)

- WS upgrade exactly matches the recipe in
  [controller_websocket_api.md](controller_websocket_api.md):
  `Sec-WebSocket-Protocol: ucp4`, `permessage-deflate;
  client_max_window_bits`, etc.
- The real controller's `Sec-WebSocket-Key` is per-connection random
  (we observed `F95OwVoAyjR/0G9QHE0tiA==`, `pfcYJkpq1/xPqjcw2yEzuw==`).
- Bridge accept: `Sec-WebSocket-Accept: <RFC6455 hash>`,
  `Server: UBNT-WS`, `Connection: Upgrade`.
- **`X-Mode` header NOT seen** in the real controller's GET. The bridge
  accepts the connection without it. The mock currently sends `X-Mode:
  0` and that also works. Header is optional, not mandatory — earlier
  binary RE on `sub_64720` may indicate `X-Mode: 0` is the only
  *accepted non-default* mode; absence falls through to default which
  is also "0".
- Frames so far in the captured idle window are **uncompressed**
  (RSV1=0). The deflate inflater in the decoder is wired up but hasn't
  been exercised. Larger messages (e.g. the `addDevice` body or 0x43
  reply) may compress — to be verified against a pair capture.

## Envelope structure (corrected)

Each WebSocket frame carries a sequence of `(prefix, json)` tuples:

- **8-byte framing prefix**: `01 01 00 00 00 00 00 <type>` for the
  primary envelope. Last byte is a single-char type code.
- A second-and-subsequent body uses prefix `02 01 00 00 00 00 00 <NN>`
  where `NN` appears to be a length byte (e.g. `0xD3 = 211` for a
  213-byte body — encoding is approximate, possibly length-2 or
  length-of-something-else; not yet pinned down).

Type code semantics — observed but **not strictly enforced**:

| code | byte | observed in        |
|------|------|--------------------|
| `q`  | 0x71 | controller→bridge requests (`bridgeInfoGet`) |
| `o`  | 0x6f | both: controller→bridge requests (`keyExchange`, `sendMessage`) AND bridge→controller events (`devsInfoChanged`, `messageReceived`) |
| `m`  | 0x6d | controller→bridge requests (`authorize`, `addDevice`) |
| `r`  | 0x72 | responses (and oddly `discoveryStart` request) |
| `J`  | 0x4a | result/payload sub-bodies (e.g. the 32B `key` in `keyExchange` response) |

**The type byte is not authoritative. The JSON's `"type"` field
(`"request"` / `"response"` / `"event"`) is the source of truth.**

## Method vocabulary (confirmed)

These are the actual `"action"` field values the controller pushes —
not the `getDeviceKey` / `startSessionKeyRenewal` strings we previously
inferred from binary strings.

### `bridgeInfoGet` (controller → bridge, request)

Empty payload. Bridge replies with hardware info:

```json
{
  "defaultIface": "radio0",
  "id": "8dccbbb6-367f-4098-8c7a-e214b674fb6f",
  "ifaces": {
    "radio0": {
      "caps": {"maxDataLen": 241, "spectralScan": true},
      "driver": "sx1302",
      "isReady": true,
      "mac": "90:41:B2:34:83:DC",
      "part": "SX1302",
      "vendor": "Semtech"
    }
  },
  "runtime": 5,
  "type": "LoRa-Bridge",
  "version": "1.1.0"
}
```

The `id` field is **stable across connections** to the same bridge —
same UUID seen on conn1 and conn2, suggesting it's the bridge's
self-identity (not the request id).

### `keyExchange` (controller → bridge, request)

Body:
```json
{"key": "<64-hex>"}
```

Response body:
```json
{"key": "<64-hex>"}
```

Both sides exchange a 32B key. This is **per-connection** — different
keys on conn1 vs conn2. Possibly a session-level key for some
controller-bridge inner protocol; not the same as the per-sensor
session key.

Captured pairs (conn2 of t0):
- controller→bridge: `65008877595120df1e09a0be1279c4efcff0577fc3248237cba389da473b0e0b`
- bridge→controller: `47991CC44452D5C3366F190D726BED19876AA42522D6B21E2E43463FA1037E2A`

(uppercase hex going up, lowercase coming down — possibly meaningful,
probably just different code paths.)

### `authorize` (controller → bridge, request)

Body:
```json
{
  "clientID": "652ee9b0-8ea3-41a9-8589-b601159ea6b6",
  "secret": "tix1aMbxBocO1VWhfS6iIQ0YsnJwjKTiU5y2qLjOBYTiAnuk2HZBbvx6Z7ws96Nc"
}
```

Response (when iface is up):
```json
{"iface": "radio0",
 "secret": "UgLML4iXufaV3MECqfwK2bJ84BgnutMvRAVFMmRz3iR+4jJvBSJ04ygMgddQxonV"}
```

Response (when iface is still booting):
```json
{"error": "Interface down", "errorCode": 7, "id": "...",
 "timestamp": ..., "type": "response"}
```

The `clientID` is **stable per controller** — same UUID on conn1 and
conn2. Likely the UniFi controller's persistent identifier.

The `secret` is rotated per-connection (different on conn1 vs conn2).
48-byte base64 = 64-char encoded. Looks random.

### `discoveryStart` (controller → bridge, request)

Empty body, empty response. Tells the bridge to begin LoRa-side
discovery. After this, `addDevice` requests can flow.

### `addDevice` (controller → bridge, request)

This is the per-sensor provisioning:

```json
{
  "mac": "9041B22E9A53",
  "key": "74909cbed4ee599e2dbad41b285918653845c72d62442840efec7878ff11dab2",
  "fallbackKey": "50403c8cf20c3158d0d998c774ddc8189049c554fab88b2483fa10fcb5e73dd1"
}
```

Response is empty `{}`. The bridge then fires a `devsInfoChanged`
event with `{"capacity":{"available":99,"max":100}}`.

**`key` and `fallbackKey` are 32B hex — these are the per-sensor
secrets the bridge needs.** They're NOT the same as the
`keypair+0x30 = c5923a86…` value we saw in pair6/7. They are also
**different from session to session for the same sensor MAC** —
captured here for `9041B22E9A53`:

- conn t0: `74909cbed4ee599e2dbad41b285918653845c72d62442840efec7878ff11dab2`
- (we'd previously captured `c5923a86…` as the gh_update arg-3 input)

So `addDevice.key` is plausibly NOT the session-key KDF input we
analysed. The KDF input we documented earlier may come from a
different field that we still haven't seen — possibly a separate
JSON-RPC method that fires only at pair time, OR derived from
`addDevice.key` somehow. **Worth a pair capture to disambiguate.**

`fallbackKey` is a new field we hadn't seen.

### `sendMessage` (controller → bridge, request)

This is the headline finding — the controller pushes raw DL bytes:

```json
{
  "mac": "9041B22E9A53",
  "data": "0b9311010d14",
  "duty": true,
  "ack": true,
  "timeout": 900000
}
```

Observed `data` values across idle + pair captures (NN is the rolling
counter we documented):

| data | bytes | meaning |
|------|-------|---------|
| `0992` / `099a` / `09a1` / etc. | 2 | 0x53 short reply (`09 NN`) |
| `0b9311010d14` etc. | 6 | 0x44 management reply (`0b NN 11 01 0d 14`) |
| `0e950d00012c` etc. | 6 | 0x4e management reply (`0e NN 0d 00 01 2c`) — **NEW pattern from idle** |
| `0ea6150001` | 5 | 0x4e short variant |
| **`029c4b144c10e0703533e445b8cbeffc3d98704bbc873ba68b13a86269b7b2cd4378cf15f1b061326f8e2c5ed91dc3b54e147696679e968d7d136df7561f02989b2b0000048f`** | **70** | **0x74 reply with the Class B grant** (`02 NN <64B middle> 00 00 04 8F`) |

**The 70-byte grant is plaintext in `sendMessage.data`** (lowercase
hex in the wire JSON). The bridge XSalsa20-encrypts it with the
session key (`df0818dc…b53e69dc` for this session) and BLAKE2b-MICs
it before transmitting as the `e0 74` DL frame. **No bridge-local
generation of the 64B middle is needed** — the bridge is a pure
relay.

This invalidates the days we spent hunting `sub_327c4` and inline
`strb` stores looking for grant-byte assembly on the bridge. The
bridge does receive the grant byte-by-byte via `std::string::push_back`,
but those bytes come from the JSON `data` field, not from internal
state.

`duty: true` likely means "respect duty-cycle limits". `ack: true`
likely means "expect MAC-layer ACK from sensor". `timeout: 900000`ms
= 15 min upper bound on TX.

The bridge later sends a `response` for each `sendMessage` after the
sensor ACKs (or timeout) — so `sendMessage` is request/response, not
fire-and-forget.

### `removeDevice` (controller → bridge, request) — NEW

Body:
```json
{"mac": "9041B22E9A53"}
```

Empty response. Tells the bridge to forget a sensor. During the
re-pair flow we observed `removeDevice` followed immediately by
`addDevice` (with new keys) — i.e. the controller rotates per-sensor
keys mid-pair after the grant is acknowledged.

## Heartbeat

WebSocket-level ping/pong every ~80s, payload is epoch-ms as ASCII:

```
TX ping payload: "1777489980"   (= 1777489980 ms = idle timestamp)
RX pong payload: "1777489980"   (echoed)
```

The bridge initiates pings; controller echoes. No JSON envelope —
pure WS control frames.

## Pair-time findings (factory-reset re-pair, 2026-04-29)

Capture: [bridge_y3_pair_20260429.log](../../captures/live/y3/bridge_y3_pair_20260429.log)
(quiet hook, 117 SSL events, 4 scalarmult, 68 BLAKE2b runs, 140

### Session-key KDF — fully confirmed

Each per-sensor session-key derivation is a single `gh_init` →
4×`gh_update(32B)` → `gh_final(32B)`. From the `state=0016fa98`
buffer we extracted four such 4-update sequences in this capture; the
one corresponding to the actual factory-reset pair has:

```
update[0] = 9ff33682a82a5bf71b42732e7dc12333e8e3373555e7bf1dbd42b547f6285003   = shared_secret (Curve25519 ECDH)
update[1] = f03370d39f9b24a896b14e02ca09f60cbcd9f416f671ac643ac4ab43e550763e   = pubkey (gw or sensor)
update[2] = 3f96d510a411566043dbd0cb835749dc20f2d62a976cea90a53417c3a047364c   = pubkey (the other one)
update[3] = c5923a86e166e4bf3f8959643ff1c245f986115ec34946ded0b87dc0d7bd38db   = addDevice.key  ← controller-provisioned per-sensor secret
final     = session_key (32B)
```

`update[3]` exactly matches the `key` field of the second `addDevice`
call (`{mac: "9041B22E9A53", key: "c5923a86…d7bd38db"}`) — the first
match between an SSL plaintext field and a BLAKE2b input we've ever
captured. **`addDevice.key` is the per-sensor secret in the documented
KDF formula.** Pinned.

### Per-pair `addDevice` call sequence (3 calls observed)

During the pair we saw three distinct `addDevice` calls for the same
sensor MAC, with three different `key` values:

| timestamp | key | fallbackKey | context |
|---|---|---|---|
| 1777490677516 | `74909cbe…ff11dab2` | `50403c8c…b5e73dd1` | idle reconnect cache (pre-pair) |
| 1777491819459 | `c5923a86…d7bd38db` | (absent) | actual factory-reset pair (this is the persistent identity) |
| 1777491833472 | `aed56bd5…cfde95d4` | `a42b0887…6fae903a` | post-grant key rotation |

Implications:
- The persistent per-sensor secret is `c5923a86…d7bd38db` (constant
  across all our pair6/7/Y3 captures).
- `fallbackKey` is **optional** — present sometimes, absent for the
  pair-critical addDevice.
- The controller rotates session keys *after* successful adoption via
  another `addDevice` call. We haven't yet confirmed whether the
  rotated key replaces the persistent one in the controller's DB or
  is a transient session-key for the immediate post-pair traffic.

### Pair flow — full chronological walk-through

```
sensor (factory reset)
  → 0x40 discovery UL
bridge → controller
  → discoveryResult event (rssi, snr, mac, adopted:false)
  → discoveryResult event (rssi, snr, mac, adopted:true)  ← controller signals adoption desired
controller → bridge
  → addDevice {mac, key=c5923a86…}
sensor ↔ bridge
  → 0x42 connection req UL (sensor pubkey)
bridge: ECDH (scalarmult) → shared_secret
bridge: blake2b(shared || pub_a || pub_b || addDevice.key) → session_key
bridge → sensor
  → 0x62 connection rsp DL  (encrypted with outer pairing key)
sensor → bridge
  → 0x43 ack UL  (2-byte body 01 00, MIC'd with session_key)
bridge → controller
  → messageReceived event (forwards the ack body)
controller → bridge
  → sendMessage {mac, data=029c…0000048f, 70B}  ← THE GRANT
bridge:
  - blake2b MIC over (header || zeros || data) → MIC
  - xsalsa20_xor(data, session_key, nonce=header||zeros||counter)
  → 0x74 DL transmitted to sensor
sensor → bridge
  → 0x54-encapsulated 0x03 UL (66B, "03 9C 8F …")  ← sensor confirms grant
bridge → controller
  → messageReceived event (66B 0x03 body)
controller → bridge
  → removeDevice {mac}
  → addDevice {mac, key=aed56bd5…, fallbackKey=a42b0887…}  ← key rotation
ACTIVE state: periodic 0x44 management heartbeats begin
```

| function | count | role |
|---|---|---|
| `crypto_scalarmult` | 4 | Curve25519 ECDH (one per session-key derivation; multi-step pair has multiple) |

## 64B grant-middle structure (analysis result, 2026-04-29)

> **REFUTED 2026-04-30.** This section's hypothesis (`[32B X25519 ephemeral
> pubkey, LE] || [32B Poly1305 MAC + ciphertext]`) was wrong. The 64B
> middle is actually `[32B gatewayPublicKey, LE] || [32B
> gatewayFallbackPublicKey, LE]` — two raw public keys, no encryption.
> Both halves are X25519 pubkeys, which is why MSB[31] is clear in
> *both* of all 8 captures (the joint MSB-clear pattern wasn't
> "u-coord + ciphertext-that-coincidentally-has-MSB-clear"; it was
> two u-coords). See
> [`superlink_application_layer.md`](superlink_application_layer.md)
> for the corrected message protocol. Kept below for the analysis
> methodology and as a record of how we got it wrong.

### Negative results (rule out trivial structures)
- **No bytes stable across all 8 grants.** Pairwise byte-diff 62-64/64,
  bit-diff ~50% — signature of independent random data.
- **No substring matches** for sensor/bridge MAC, `addDevice.key`,
  BLAKE2b inputs (`9ff33682…`, `f03370d3…`, `3f96d510…`),
  `session_key`, `ssid`, in either byte order, at any offset.
- **No timestamps** (no plausible epoch-s/ms hits beyond random
  background).
- **No ASCII runs** (Y3 has 26/64 printable bytes — matches uniform).
- **Entropy 5.81 bits/byte** for Y3 middle, 7.60 bits/byte across all
  8 middles concatenated — uniformly random within tolerance.

### Positive signal — the headline
- **byte[31] has MSB-clear in all 8 captures.**
  Values: 0x50, 0x75, 0x79, 0x19, 0x43, 0x48, 0x2b, 0x78.
- **byte[63] has MSB-clear in all 8 captures.**
  Values: 0x3b, 0x21, 0x65, 0x69, 0x32, 0x4a, 0x67, 0x2b.
- Joint probability under uniform random: **1/65,536 ≈ 0.0015%.**
  Not noise.
- This is the exact signature of **two little-endian Curve25519
  X25519 u-coordinates** (RFC 7748 §5 masks the top bit during
  encoding). Confirmed plausible: the 32B halves of two known
  Curve25519 keys from this session (the BLAKE2b update[1] and
  update[2] = the gw/sensor pubkeys) show MSB-clear in their last
  byte (`3e`, `4c`).

### Hypothesis

```
64B grant middle = [32B ephemeral X25519 pubkey, LE]
                || [32B authenticated ciphertext (~16B MAC + 16B ct)]
```

Mechanism most consistent with the data:
- Controller generates a fresh per-pair ephemeral X25519 keypair.
- Computes a shared secret with the sensor's known static pubkey
  (which lives in the controller's per-sensor DB alongside
  `addDevice.key`).
- Derives a one-shot encryption key (likely BLAKE2b of the shared
  secret + `addDevice.key`).
- Encrypts ~16 bytes of payload (probably the next-session symmetric
  key, or a Class B activation seed) under XSalsa20-Poly1305.
- Concatenates: `[ephemeral_pubkey_LE, 32B] || [poly1305 MAC, 16B] || [ciphertext, 16B]` = 32B + 32B = 64B.
- Sensor side: knows its own static private key, recovers the shared
  secret, derives the same one-shot key, MAC-verifies, decrypts.

### Less likely alternatives
- **Ed25519 signature `R||S`**: ruled weak. Only 0/8 captures have S<L
  under LE interpretation, so signature structure is absent.

### `NN` field behaviour
`NN` (the 2nd byte of the 70B grant body, before the middle) is a
**rolling byte counter** that wraps mod 256. Apr-21 session cycle:
0x47→0x5a→0x6b→0x7e→0x8e→0x9d→0xaa (deltas 13-19). Apr-29 fresh
session restarts at 0x9c. Likely tied to total bridge-issued grants
or pair counter.

### Verification path (if Y4 stalls)

Two ways to test the hypothesis directly:
1. **From our captures**: take a captured grant, attempt X25519 scalar
   multiplication of the first 32B (treated as u-coord) against the
   gateway's known static private key (which we've captured via
   `crypto_scalarmult` hook) — if a valid shared secret comes out,
   feed it into BLAKE2b alongside `addDevice.key` to derive the trial
   one-shot key, then attempt Poly1305 verification on the second 32B.
   A successful MAC verify confirms the structure and reveals the 16B
   plaintext.
2. **From the controller**: hook libsodium's `crypto_box_*` /
   `crypto_secretbox_*` calls in the UniFi Network app process. The
   plaintext + key would be visible right before the JSON-RPC call.

For the open-gateway implementation: if we control the controller (we
do — it's our mock), we don't need to crack the algo at all. We just
generate our own grants the same way the real controller does — pick
an ephemeral key, ECDH against sensor static pubkey, encrypt 16B of
intent, ship the 70-byte body. Y4 doesn't depend on this analysis.
